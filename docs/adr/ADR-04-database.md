# ADR-04: Использование одной PostgreSQL базы данных

## Status
...

## Context

Система состоит из нескольких сервисов:
- API Gateway (DRF)
- Аналитический сервис (FastAPI)

Оба сервиса работают с данными:
- пользователи, устройства, измерения (DRF)
- результаты аналитики и агрегаты (FastAPI)

Возникает вопрос:
как организовать хранение данных?

Рассматривались варианты:
1. Одна общая база данных PostgreSQL
2. Отдельная база данных для каждого сервиса

Ключевые требования:
- простота разработки и поддержки
- согласованность данных
- минимизация сетевых задержек
- возможность масштабирования в будущем

## Decision

Использовать одну общую PostgreSQL базу данных для всех сервисов.

При этом:
- логически разделить данные по таблицам
- DRF управляет своими таблицами (пользователи)
- FastAPI работает со своими таблицами (аналитика, устройства, измерения, агрегаты)

Пересечение таблиц между сервисами минимизировано.

## Consequences

### 👍 Плюсы

- Простота архитектуры
  - меньше инфраструктуры
  - проще развертывание и поддержка

- Отсутствие необходимости синхронизации данных
  - нет дублирования данных между сервисами
  - нет необходимости в event-driven механизмах

- Низкие задержки
  - нет сетевых вызовов между БД

- Удобство разработки
  - единая точка доступа к данным
  - проще отладка

- Логическое разделение таблиц
  - каждая подсистема работает со своим набором таблиц
  - конфликты между сервисами исключены на уровне структуры данных

- Гибкость на старте проекта
  - позволяет быстрее реализовать MVP

### 👎 Минусы

- Слабая изоляция сервисов
  - сервисы зависят от одной БД

- Ограниченная независимость масштабирования
  - сложнее масштабировать БД по частям

- Риск нарушения границ ответственности
  - сервисы могут начать обращаться к "чужим" таблицам

- Общая точка отказа
  - падение БД влияет на все сервисы

## Alternatives

### 1. Отдельная база данных для каждого сервиса

Плюсы:
- строгая изоляция сервисов
- независимое масштабирование
- лучше соответствует микросервисной архитектуре

Минусы:
- необходимость синхронизации данных
- усложнение архитектуры (event-driven, очереди)
- увеличение задержек
- сложность поддержки

Причина отказа:
избыточная сложность для текущего этапа проекта (MVP),
при отсутствии значительных преимуществ.

---

### 2. Общая база без логического разделения (общие таблицы)

Плюсы:
- простота

Минусы:
- высокая вероятность конфликтов
- отсутствие границ ответственности
- сложность поддержки

Причина отказа:
не обеспечивает изоляцию данных между сервисами.
