# ADR-03: Использование FastAPI для аналитического сервиса

## Status
...

## Context

В системе предусмотрен отдельный сервис для аналитики (см. ADR-02),
который выполняет:
- обработку данных энергопотребления
- вычисление агрегатов и метрик
- потенциально длительные и ресурсоёмкие операции
- возможное расширение в сторону машинного обучения

Ключевые требования к аналитическому сервису:
- высокая производительность
- поддержка асинхронности
- эффективная обработка I/O операций
- простота написания API для внутренних сервисов
- хорошая работа с Python-экосистемой (numpy, pandas и др.)

Рассматривались варианты:
- Django REST Framework (DRF)
- FastAPI

## Decision

Для реализации аналитического сервиса выбран FastAPI.

FastAPI используется как отдельный микросервис, который:
- обрабатывает аналитические запросы от DRF
- выполняет вычисления
- поддерживает асинхронные операции
- предоставляет HTTP API для внутреннего взаимодействия

## Consequences

### 👍 Плюсы

- Нативная асинхронность (async/await)
  - эффективная обработка I/O (запросы к БД, внешние сервисы)
  - лучшее использование ресурсов

- Высокая производительность
  - меньше overhead по сравнению с Django
  - подходит для вычислительных задач

- Лёгковесность
  - проще и быстрее поднимается сервис
  - меньше лишней инфраструктуры

- Удобная работа с типами (Pydantic)
  - валидация данных
  - автогенерация схем

- Отличная интеграция с научными библиотеками
  - numpy, pandas, scikit-learn

- Встроенная документация (Swagger/OpenAPI)
  - упрощает взаимодействие между сервисами

### 👎 Минусы

- Нет встроенной ORM и полноценной модели пользователей
  - требуется отдельная настройка (если нужно)

- Меньше "из коробки"
  - часть функциональности нужно реализовывать вручную

- Не подходит как основной API Gateway
  - слабее в управлении сложной бизнес-логикой

## Alternatives

### 1. Django REST Framework (DRF)

Плюсы:
- встроенная ORM
- готовая система пользователей и прав
- удобен для CRUD и бизнес-логики

Минусы:
- синхронная модель по умолчанию
- более тяжёлый фреймворк
- избыточен для вычислительного сервиса
- хуже подходит для высоконагруженных аналитических задач

Причина отказа:
DRF ориентирован на бизнес-логику и CRUD, а не на вычислительные и асинхронные задачи.
Использование DRF для аналитики привело бы к избыточности и снижению производительности.

---

### 2. Реализация аналитики внутри DRF

Плюсы:
- простота
- меньше сервисов

Минусы:
- смешение ответственности
- блокировка API при долгих вычислениях
- сложность масштабирования

Причина отказа:
нарушает разделение ответственности и ухудшает устойчивость системы.
