# ADR-02: Вынесение аналитики в отдельный сервис

## Status
...

## Context

Система должна обрабатывать и анализировать данные энергопотребления.
Аналитика может включать:
- агрегации (средние, пики, тренды)
- сложные вычисления
- потенциально долгие операции
- расширение в сторону ML в будущем

Основной backend (DRF) уже выполняет:
- аутентификацию и авторизацию (JWT)
- CRUD операции
- управление бизнес-логикой

Возникает вопрос:
где должна выполняться аналитика?

Рассматривались варианты:
1. Выполнять аналитику внутри DRF (монолит)
2. Вынести аналитику в отдельный сервис (FastAPI)

Ключевые требования:
- масштабируемость
- изоляция тяжелых вычислений
- возможность асинхронной обработки
- гибкость для развития аналитики

## Decision

Аналитика вынесена в отдельный сервис, реализованный на FastAPI.

DRF (API Gateway):
- принимает запрос от клиента
- при необходимости отправляет запрос в аналитический сервис

FastAPI:
- выполняет вычисления
- обрабатывает аналитические задачи
- может работать асинхронно
- взаимодействует с базой данных

## Consequences

### 👍 Плюсы

- Разделение ответственности
  - DRF: бизнес-логика и API
  - FastAPI: вычисления и аналитика

- Масштабируемость
  - аналитический сервис можно масштабировать отдельно

- Изоляция нагрузки
  - тяжелые вычисления не блокируют API Gateway

- Готовность к асинхронности
  - легко добавить очереди (Celery, Redis)

- Гибкость развития
  - можно добавлять ML, batch processing, streaming

- Возможность независимого деплоя
  - сервисы развиваются отдельно

### 👎 Минусы

- Усложнение архитектуры
  - появляется межсервисное взаимодействие

- Сетевые задержки
  - HTTP-вызовы между сервисами

- Необходимость обработки ошибок
  - таймауты, ретраи, отказ сервиса

- Усложнение отладки
  - логика распределена между сервисами

- Требуется управление контрактами API
  - важно синхронизировать DRF и FastAPI

## Alternatives

### 1. Аналитика внутри DRF (монолит)

Плюсы:
- проще реализация
- нет сетевых вызовов
- легче отладка

Минусы:
- блокировка запросов при долгих вычислениях
- ухудшение производительности API
- сложнее масштабировать
- смешение ответственности

Причина отказа:
аналитика может стать узким местом и ухудшить стабильность API Gateway.

---

### 2. Асинхронные задачи внутри DRF (Celery без выделенного сервиса)

Плюсы:
- частичное решение проблемы нагрузки
- нет отдельного сервиса

Минусы:
- логика всё равно остаётся в одном сервисе
- усложнение кода DRF
- ограниченная изоляция

Причина отказа:
не обеспечивает полной независимости и масштабируемости аналитики.
